# S1 意图 · 文件系统网盘化改造

> change-id: 20260830-drive-war ｜ 创建: 2026-08-30 ｜ 状态: 待 owner 拍板 S2 后进入 S3

## 一、背景（为什么做）

owner 原话（2026-08-30）：「把文件目录做成网盘形式，像 Windows 资源管理器：可创建多层文件夹、一个项目一个文件夹、用户可创建/修改/删除、权限继承组织架构、仅项目成员可见和下载。当前的文件目录只能做文件索引，不能作为层级目录，肯定是不行的。」并授权设计发挥（「其他你们想想应该怎么更好的设计」）。

现状痛点：现有 /files 页是「交付计划管理」——左侧目录树是流程引擎按模板自动生成的 20 个阶段目录（不可自由增删），右侧是 FileRequirement 条目表（审批/归档导向）。用户无法自由建目录、无法随意存放文件（无条目概念就没法定义"归属"）、没有回收站、没有跨项目搜索。它本质是交付计划的索引器，不是文件管理器。

## 二、目标（做成什么样）

1. 每个项目拥有一棵**网盘目录树**：任意层级自建文件夹、重命名、移动、删除（回收站保护），交互对标 Windows 资源管理器 / 主流网盘
2. 文件自由上传（多文件/拖拽）到任意目录，支持下载（批量打包）、移动、重命名、预览（复用现有 preview）
3. 权限：**仅项目成员可见和下载**为底线；文件夹权限可继承组织架构（部门维度）；与现有三层权限引擎（permission.ts）整合而非另起炉灶
4. 前端形态：左树右列表 + 面包屑；PC 与 App（WebView）均可用
5. 全程审计（创建/删除/移动/下载留痕）

## 三、非目标（明确不做）

- 不做团队级/公司级公共网盘（本期只做**项目级**网盘，一个项目一个网盘）
- 不做外链分享、公开链接（涉及安全面扩大，列入二期待拍板）
- 不做文件内容全文检索（一期只做文件名搜索）
- 不做文件在线协同编辑
- 不做物理存储结构搬迁（uploads 目录不动，物理路径与逻辑目录解耦）

## 四、核心设计矛盾（本战役成败关键）

现有文件体系是「**流程驱动**」的（FileCatalog=阶段目录树/FileRequirement=交付条目/File=版本化文件），支撑审批流/待办/催办/归档拦截等核心业务，**不能拆**。owner 要的网盘是「**用户驱动**」的自由文件区。矛盾点：

| # | 冲突点 | 边界定义（S1 定调） |
|---|--------|---------------------|
| C1 | 阶段目录是系统生成的（用户不该删），网盘目录是用户自由的 | 必须能在同一模型内区分「系统保护目录」与「用户自建目录」，系统目录禁删禁改名，用户目录自由 |
| C2 | FileRequirement 挂在阶段目录下（审批/归档拦截依赖它），网盘文件没有条目概念 | 条目与自由文件必须共存于一棵树/一个视图，互不干扰；条目在网盘视图以带状态徽章的形式呈现 |
| C3 | File 表无目录列（靠 storagePath 前缀耦合） | 必须补显式目录外键 + 存量数据回填，且物理文件不搬迁（路径与逻辑解耦） |
| C4 | 现有权限是「项目角色基线+条目范围终审」，没有文件夹级部门继承 | 文件夹权限必须复用 ResourcePermission（FILE_FOLDER+DEPARTMENT 主体已就绪），沿树继承，不另造权限体系 |

**共存策略三选一**（详细论证见 spec.md §2）：双轨制 / 融合制 / 替代制。S1 倾向**融合制**（同一棵目录树，阶段目录降级为受保护的系统文件夹，条目作为特殊文件行呈现），理由：模型改动最小、零数据搬迁、用户体验一个入口不分裂。**最终以 owner 拍板为准。**

## 五、成功判据

- 项目成员在任意项目下可完成「建文件夹→上传→移动→重命名→删除→回收站恢复→下载/打包」全链路操作
- 阶段目录与交付条目功能不受任何影响（审批/归档拦截回归全绿）
- 非项目成员无法看到/下载该项目任何网盘文件（越权用例全红）
- App（WebView）内可正常浏览与上传
